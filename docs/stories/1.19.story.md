# Story 1.19 — Unificar Fonte de Dados de Entregas

**Status:** Ready
**Epic:** 1 — Qualidade e UX do Chatbot
**Story ID:** 1.19
**Prioridade:** Alta
**Estimativa:** M (3–4h de investigação + edição no n8n)

---

## Descrição

Existem dois caminhos no fluxo que buscam entregas para o mesmo projeto usando **tabelas/views completamente diferentes**:

| Caminho | Nó | Fonte | Filtro |
|---------|-----|-------|--------|
| Via `PreparaEntregas` | `ConsultaEntregas` | Tabela `CRONOGRAMA` | `FG_MARCO = 1` (só marcos) |
| Via seleção direta | `ConsultaEntregas1` | View `VW_BI_VDBCRONOGRAMA` | `IN ('Entrega', 'Marco')` |

Os dois caminhos podem retornar conjuntos de dados diferentes para o mesmo projeto:
- `CRONOGRAMA.FG_MARCO = 1` filtra apenas marcos
- `VW_BI_VDBCRONOGRAMA IN ('Entrega', 'Marco')` retorna entregas + marcos

Além disso, os nomes das colunas diferem (`DESCRICAO_ATIVIDADE`/`PERCENTUAL_EXECUTADO` vs `Nome`/`% Executada`), e a view usa colunas com acentos em aspas duplas — frágil.

Esta story define qual é a fonte canônica, migra ambos os caminhos para ela, e elimina a duplicidade.

**Valor:** Dados consistentes independente de como o usuário chega à tela de Entregas. Elimina confusão e bug potencial onde o mesmo projeto mostra entregas diferentes em momentos diferentes.

---

## Workflow de Desenvolvimento

```
1. INVESTIGAÇÃO (fazer antes de editar):
   a. Confirmar quais colunas existem em CRONOGRAMA e VW_BI_VDBCRONOGRAMA
   b. Executar ambas as queries para o mesmo PROJETO_ID de teste
   c. Comparar resultados — quantidade e conteúdo
   d. Decidir a fonte canônica (ver AC-1)
   
2. Importar docs/flow/projeta-sc.json no n8n (Settings → Import)
3. Migrar ambos os caminhos para a fonte escolhida (AC-2 ou AC-3)
4. Testar via WhatsApp para os dois caminhos de chegada
5. Exportar e substituir docs/flow/projeta-sc.json
6. Commitar
```

## Acceptance Criteria

### AC-1: Investigação e decisão documentada

- [ ] Executar no banco:
  ```sql
  -- Fonte A
  SELECT C.DESCRICAO_ATIVIDADE, C.PERCENTUAL_EXECUTADO
  FROM CRONOGRAMA C
  WHERE C.FG_MARCO = 1 AND C.PROJETO_ID = {id_de_teste}
  ORDER BY C.ORDEM;

  -- Fonte B
  SELECT "Nome", "% Executada"
  FROM VW_BI_VDBCRONOGRAMA
  WHERE "Cód. projeto" = {id_de_teste}
  AND "Tipo de informação" IN ('Entrega', 'Marco')
  ORDER BY "NUORDEM";
  ```
- [ ] Registrar no Change Log desta story:
  - Qual ID de projeto foi usado no teste
  - Quantas linhas cada fonte retornou
  - Se os dados diferem (e por quê)
  - Qual foi escolhida como canônica e o motivo

### AC-2: Se fonte canônica = `VW_BI_VDBCRONOGRAMA` (view BI)
- [ ] `PreparaEntregas` migrado para usar a view ao invés de `CRONOGRAMA`
- [ ] Colunas com acentos substituídas por aliases sem acentos (ex: `"Cód. projeto"` → confirmar alias disponível)
- [ ] Filtro inclui `IN ('Entrega', 'Marco')` (consistente com o que já existe em `ConsultaEntregas1`)
- [ ] Nó `ConsultaEntregas` (que recebia a query de `PreparaEntregas`) usa a mesma estrutura de `ConsultaEntregas1`

### AC-3: Se fonte canônica = tabela `CRONOGRAMA`
- [ ] `ConsultaEntregas1` migrado para usar `CRONOGRAMA` com `FG_MARCO = 1`
- [ ] `PreparaEntregas` ajustado para incluir também entregas (não só marcos) se `FG_MARCO = 0` para entregas e `FG_MARCO = 1` para marcos — investigar a semântica do campo
- [ ] Ambos os nós usam as mesmas colunas (`DESCRICAO_ATIVIDADE`, `PERCENTUAL_EXECUTADO`)

### AC-4: Coluna nula de percentual de execução tratada

- [ ] Se `PERCENTUAL_EXECUTADO` ou `% Executada` for null para uma entrega, o `FormataEntregas` não exibe `null%` ou `undefined%`
- [ ] Verificar que `FormataEntregas` usa `e.PERC_EXECUTADO !== null` (já existe no código — confirmar que está correto após a migração)

### AC-5: Nó redundante removido ou claramente desativado

- [ ] Após unificação, o nó do caminho não-canônico é removido ou tem um comentário explicando por que foi mantido
- [ ] O fluxo não tem dois caminhos ativos para entregas que retornam dados diferentes

## Escopo

**IN:**
- Investigação das duas fontes no banco

## Riscos

- **Dados divergentes entre fontes:** Se as duas fontes retornam conjuntos diferentes, a escolha pode impactar o que os cidadãos veem. Documentar a divergência e comunicar ao cliente antes de implementar.
- **VW_BI_VDBCRONOGRAMA pode estar desatualizada:** Views de BI às vezes têm refresh programado. Se a view não está em tempo real, usar a tabela `CRONOGRAMA` é mais confiável.
- **FG_MARCO semântica:** `FG_MARCO = 1` pode significar apenas "marco" (milestone), excluindo entregas intermediárias. Se for isso, a tabela `CRONOGRAMA` sem esse filtro pode ser mais completa. Investigar com o DBA ou documentação do banco.
