# Story 1.15 — Validar PROJETO_ID para Prevenir SQL Injection

**Status:** Ready
**Epic:** 1 — Qualidade e UX do Chatbot
**Story ID:** 1.15
**Prioridade:** Alta
**Estimativa:** S (2–3h de edição no n8n)

---

## Descrição

Seis nós constroem queries Oracle interpolando `PROJETO_ID` diretamente no SQL sem nenhuma validação:

```javascript
// PreparaEntregas — exemplo do problema
"WHERE C.PROJETO_ID = " + id

// ConsultaValores — exemplo no nó HTTP
"WHERE PROJETO_ID = {{ $json.projeto.PROJETO_ID }}"
```

`PROJETO_ID` vem de uma query anterior (não do usuário diretamente), então o risco prático é baixo — mas não é zero. Se o valor vier corrompido ou manipulado por um payload intermediário, o SQL seria executado sem defesa.

A correção é simples: validar que o valor é um inteiro antes de usar. Uma linha de JavaScript em cada nó Code, e um filtro de expressão nos nós HTTP Request.

**Valor:** Elimina a classe de risco por design. Baixo esforço, alto padrão de segurança.

## Acceptance Criteria

### AC-1: PreparaEntregas — validação de id
- [ ] Antes de usar `id` na query, validar:
  ```javascript
  const id = parseInt(input.projeto.PROJETO_ID, 10);
  if (isNaN(id) || id <= 0) throw new Error('PROJETO_ID inválido: ' + input.projeto.PROJETO_ID);
  ```
- [ ] A query SQL usa a variável `id` (número) — nunca `input.projeto.PROJETO_ID` diretamente

### AC-2: PreparaContratos — validação de id
- [ ] Mesma validação do AC-1 aplicada antes de construir o SQL
- [ ] A query SQL usa `id` (número inteiro validado)

### AC-3: ConsultaValores (nó HTTP Request) — expressão protegida
- [ ] O campo `query` alterado para incluir validação inline via expressão n8n:
  ```
  =SELECT ... FROM FINANCEIRO WHERE PROJETO_ID = {{ parseInt($json.projeto.PROJETO_ID) || 0 }}
  ```
- [ ] Ou: mover a query para um nó Code antecessor com validação explícita e passar o SQL montado

### AC-4: ConsultaEntregas1 (nó Oracle) — expressão protegida
- [ ] Campo `query` usa `parseInt` no valor interpolado:
  ```
  WHERE "Cód. projeto" = {{ parseInt($json.projeto.PROJETO_ID) || 0 }}
  ```

### AC-5: ConsultaValores1 (nó Oracle) — expressão protegida
- [ ] Campo `query` usa `parseInt` no valor interpolado:
  ```
  WHERE CODIGO_PROJETO = {{ parseInt($json.projeto.PROJETO_ID) || 0 }}
  ```

### AC-6: ConsultaContratos1 (nó Oracle) — expressão protegida
- [ ] Campo `query` usa `parseInt` no valor interpolado:
  ```
  WHERE PROJETO_ID = {{ parseInt($json.PROJETO_ID) || 0 }}
  ```

### AC-7: Comportamento com id inválido
- [ ] Se `PROJETO_ID` não for um inteiro positivo, a query não é executada (erro controlado)
- [ ] O bot não quebra silenciosamente — o erro é propagado e capturado pelo fluxo

## Cenários de Teste

| Cenário | Ação | Resultado esperado |
|---------|------|--------------------|
| Fluxo normal | Selecionar projeto e ver entregas, valores, contratos | Funciona normalmente |
| ID válido | PROJETO_ID = 1234 | Query executada normalmente |
| ID zero | PROJETO_ID = 0 | Query retorna vazio (WHERE PROJETO_ID = 0 não encontra nada) |
| ID não-numérico | PROJETO_ID = "abc" | Erro controlado, não executa SQL |

---

## Escopo

**IN:**
- Adição de `parseInt` + validação em `PreparaEntregas` e `PreparaContratos` (nós Code)
- Uso de `parseInt()` nas expressões dos nós Oracle `ConsultaValores`, `ConsultaEntregas1`, `ConsultaValores1`, `ConsultaContratos1`

**OUT:**
- Parameterização real de queries (Oracle driver no n8n não suporta bind params nativamente)
- Alteração na lógica de negócio dos nós
- Sanitização de campos de texto livre (nome, município, etc.) — esses usam `escapeSql()` existente

---

## Dependências

- Nenhuma — pode ser implementada isoladamente

---

## Riscos

- **parseInt com valor null:** `parseInt(null, 10)` retorna `NaN` — o `|| 0` cobre esse caso. Verificar que `NaN || 0` = `0` em JavaScript (correto).
