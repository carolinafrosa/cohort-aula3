# Story 1.35 — Notificações Proativas de Atualização de Projeto

**Status:** Ready
**Epic:** 1 — Qualidade e UX do Chatbot
**Story ID:** 1.35
**Prioridade:** Baixa
**Estimativa:** G (8–12h)

---

## Descrição

Após um cidadão consultar um projeto, ele precisa voltar ativamente ao chatbot para verificar atualizações. O bot nunca toma a iniciativa de avisar que algo mudou.

Esta story implementa um sistema de **notificações proativas**: quando um usuário consulta um projeto, o sistema registra o interesse. Periodicamente (via n8n scheduled trigger), o sistema verifica se houve mudanças de status, valor ou andamento nos projetos consultados, e notifica os interessados via WhatsApp.

*"Olá! O projeto 'Duplicação da BR-101' que você consultou avançou de fase: agora está em 'Em execução' (antes: 'Em licitação'). Quer mais detalhes?"*

**Valor:** Transforma o bot de sistema reativo em assistente proativo. Cria engajamento contínuo e diferencia a solução de qualquer portal web estático.

---

## Workflow de Desenvolvimento

```
1. Criar tabela no Supabase:
   CREATE TABLE project_watch (
     id SERIAL PRIMARY KEY,
     phone_number TEXT NOT NULL,
     project_id TEXT NOT NULL,
     project_name TEXT,
     last_status TEXT,
     last_value NUMERIC,
     last_checked TIMESTAMPTZ DEFAULT NOW(),
     created_at TIMESTAMPTZ DEFAULT NOW(),
     UNIQUE(phone_number, project_id)
   );

2. Modificar fluxo principal: após exibir resultado de projeto, criar nó
   "RegistraInteresse" que insere/atualiza o watch no Supabase

3. Criar um SEGUNDO FLUXO n8n (Scheduled Trigger, diário às 8h):
   a. Buscar todos os project_watch únicos (IDs de projeto distintos)
   b. Para cada projeto, consultar status/valor atual no Oracle
   c. Comparar com last_status/last_value armazenado
   d. Se houve mudança: enviar notificação via Evolution API para todos os
      numbers que assistem aquele projeto
   e. Atualizar last_status, last_value e last_checked no Supabase

4. Criar nó "OptOut": usuário pode responder "parar" para remover todos os watches

5. Testar: registrar interesse, modificar dado no Oracle, aguardar trigger → notificação
6. Exportar flows e commitar
```

## Acceptance Criteria

### AC-1: Registro de interesse automático
- [ ] Após o usuário visualizar um resultado de projeto, o nó `RegistraInteresse` cria ou atualiza um registro em `project_watch` com o project_id, phone_number e status atual
- [ ] O usuário não precisa fazer nada — o interesse é registrado automaticamente

### AC-2: Scheduled trigger de verificação
- [ ] Um segundo fluxo n8n com Scheduled Trigger (diário às 8h00) verifica mudanças em todos os projetos monitorados
- [ ] O trigger consulta o Oracle e compara status/valor com o armazenado no Supabase

### AC-3: Notificação proativa enviada
- [ ] Quando mudança é detectada, todos os números que assistem aquele projeto recebem notificação via Evolution API
- [ ] A notificação menciona: nome do projeto, o que mudou (status anterior → novo), e convite para ver mais detalhes

### AC-4: Opt-out funcional
- [ ] Usuário pode responder "parar notificações" e todos os seus watches são removidos
- [ ] O fluxo principal detecta esse comando e confirma a remoção

### AC-5: Sem spam
- [ ] O mesmo projeto não gera mais de uma notificação por dia por usuário
- [ ] Projetos sem mudança não geram notificação

## Cenários de Teste

| Cenário | Ação | Resultado esperado |
|---------|------|--------------------|
| Primeiro interesse | Consultar projeto | Watch criado no Supabase |
| Mudança de status | Alterar status no Oracle | Notificação enviada no próximo trigger |
| Sem mudança | Trigger executar sem mudança | Sem notificação |
| Opt-out | Responder "parar" | Watches removidos, confirmação enviada |
| Mesmo projeto, múltiplos usuários | 3 usuários consultam o mesmo projeto | Todos recebem notificação quando projeto muda |

## Escopo

**IN:**
- Tabela `project_watch` no Supabase
- Nó `RegistraInteresse` no fluxo principal
- Fluxo separado de verificação agendada (diário)
- Notificação proativa via Evolution API
- Opt-out simples

**OUT:**
- Notificações em tempo real (webhook Oracle — não disponível)
- Frequência configurável por usuário
- Interface de gerenciamento de watches
- Notificações por e-mail ou outro canal

## Dependências

- Story 1.31 (memória persistente) — Supabase já configurado
- Credenciais Supabase disponíveis no n8n
- **Pré-condição bloqueante:** Verificar com o administrador da Evolution API se a instância `Projeta_SC` suporta envio de mensagens proativas (outbound iniciadas pelo bot, sem template aprovado pelo WhatsApp Business). Se não suportar, esta story é inviável sem migração de instância. Resultado deve ser documentado no Change Log antes de iniciar implementação.

---

## Riscos

- **Evolution API bloqueia mensagens proativas:** WhatsApp Business API tem restrições para mensagens iniciadas pelo bot (não por usuário) — verificar política da Evolution API e se a instância usa WhatsApp Business ou pessoal
- **Volume de notificações:** Com muitos projetos monitorados e mudanças frequentes no Oracle, o trigger pode gerar muitas mensagens — adicionar rate limiting (máx 100 notificações/execução)
- **Oracle sem campo de auditoria de mudança:** Se o banco não tem `DATA_ATUALIZACAO`, pode ser difícil detectar mudanças precisas → usar hash dos campos principais como proxy
