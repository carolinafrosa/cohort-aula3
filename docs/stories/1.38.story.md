# Story 1.38 — Corrige resolução ambígua do campo `tipo` ao buscar por "obra"

**Status:** InProgress
**Epic:** 1 — Qualidade e UX do Chatbot
**Story ID:** 1.38
**Prioridade:** Alta
**Estimativa:** S (1–2h)

---

## Descrição

Ao digitar "obra", "obras" ou qualquer palavra que esteja contida em múltiplos tipos do banco (ex.: "obra portuária", "obra hídrica", "Aporte Financeiro - Obras Federais"), o nó `AplicaFiltrosResolvidos` resolve o campo `tipo` como **exato** para o **primeiro** tipo da lista que contém essa palavra.

Isso faz o `MontaBusca` gerar SQL com `=` em vez de `LIKE`, filtrando apenas aquele tipo único — o usuário perde todos os outros projetos com tipos que também contêm "obra".

**Exemplo reportado:** busca por "obra" retornava somente projetos do tipo "Aporte Financeiro - Obras Federais" quando existem também "obra portuária", "obra hídrica", "obras", etc.

**Causa raiz:** a função `encontrarExato` em `AplicaFiltrosResolvidos` usa `.find()` e retorna o primeiro match por substring sem verificar se há múltiplos matches. Quando `campos_resolvidos.tipo = true`, o `MontaBusca` usa `=` exato.

---

## Acceptance Criteria

### AC-1: Busca ambígua usa LIKE
- [ ] Ao buscar "obra", o filtro SQL usa `LIKE '%obra%'`, retornando projetos de todos os tipos que contêm "obra"
- [ ] Ao buscar "obras", idem

### AC-2: Busca específica continua exata
- [ ] "obras rodoviárias" ainda resolve como exato `= 'Obras Rodoviárias'` quando há match único
- [ ] "obra portuária" resolve como exato quando há match único na lista do banco
- [ ] Tipos com nome exatamente igual ao input (normalizado) continuam resolvendo exato

### AC-3: Nenhuma regressão
- [ ] Buscas por município, órgão, situação não são afetadas
- [ ] Busca por "convenio" (se ambíguo) também usa LIKE
- [ ] Busca por "Aporte Financeiro - Obras Federais" (completo) ainda resolve exato
