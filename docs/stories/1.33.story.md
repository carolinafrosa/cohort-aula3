# Story 1.33 — Busca Semântica com RAG sobre Catálogo de Projetos

**Status:** Ready
**Epic:** 1 — Qualidade e UX do Chatbot
**Story ID:** 1.33
**Prioridade:** Baixa
**Estimativa:** XG (>10h — considerar Epic separado)

---

## Descrição

O `MontaBusca` gera queries SQL baseadas em LIKE com os termos extraídos pelo LLM. Isso funciona para buscas exatas mas falha para perguntas semânticas vagas: *"projetos de mobilidade sustentável"*, *"obras de proteção ambiental"*, *"infraestrutura para comunidades carentes"* — termos que existem conceitualmente mas não como strings no banco.

Esta story implementa **RAG (Retrieval-Augmented Generation)** sobre o catálogo de projetos: indexar as descrições de todos os projetos em embeddings vetoriais e permitir busca semântica por similaridade como complemento (não substituto) da busca SQL.

```
Pergunta do usuário
    → Busca SQL (MontaBusca) — mantida para buscas exatas
    → Busca vetorial (novo) — para consultas semânticas vagas
    → Merge de resultados → exibição unificada
```

**Valor:** Única mudança que permite perguntas abertas e vagas retornarem resultados relevantes. Transforma o chatbot de "sistema de busca por nome" em "assistente de consulta semântica". Alto esforço mas potencial de expansão de caso de uso.

---

## Workflow de Desenvolvimento

```
1. FASE DE INDEXAÇÃO (fora do n8n):
   a. Exportar descricao + categoria + municipio de todos os projetos do Oracle
   b. Gerar embeddings via API OpenAI (text-embedding-3-small) ou Groq
   c. Armazenar embeddings no Supabase com pgvector (extensão vector)
   d. Criar função de busca por similaridade: match_projects(query_embedding, threshold, limit)

2. FASE DE INTEGRAÇÃO NO N8N:
   a. Criar nó "BuscaSemantica" (HTTP Request → Supabase RPC):
      - Input: embedding da pergunta do usuário
      - Output: top 5 projetos por similaridade
   b. Criar nó "GeraEmbeddingConsulta" (HTTP Request → OpenAI):
      - Input: texto da consulta do usuário
      - Output: vector de embedding
   c. Criar nó "MergeResultados": combinar resultados SQL + semânticos (deduplicar por ID)
   d. Inserir no fluxo após MontaBusca

3. FASE DE ATUALIZAÇÃO DO ÍNDICE:
   a. Criar script de re-indexação (cron job diário ou manual)
   b. Detectar projetos novos ou com descricao alterada e atualizar embeddings

4. Testar com consultas semânticas vagas
5. Exportar e substituir docs/flow/projeta-sc.json
6. Commitar
```

## Acceptance Criteria

### AC-1: Índice vetorial criado no Supabase
- [ ] Extensão `pgvector` habilitada no Supabase
- [ ] Tabela `project_embeddings` com campos: `project_id`, `embedding` (vector), `descricao`, `categoria`, `municipio`, `updated_at`
- [ ] Todos os projetos com descrição não-nula indexados

### AC-2: Busca semântica integrada ao fluxo
- [ ] Nó `GeraEmbeddingConsulta` converte a consulta do usuário em embedding
- [ ] Nó `BuscaSemantica` retorna top 5 projetos com similarity > 0.75
- [ ] Resultados semânticos são mesclados com resultados SQL (sem duplicatas)

### AC-3: Fallback para busca SQL apenas
- [ ] Se a busca vetorial falhar (timeout, erro de API), o fluxo continua apenas com a busca SQL — sem impacto na experiência

### AC-4: Atualização do índice
- [ ] Script de re-indexação documentado e funcional
- [ ] Projetos novos adicionados ao Oracle aparecem na busca semântica após re-indexação

### AC-5: Consultas semânticas funcionam
- [ ] Buscar "projetos verdes" retorna projetos de saneamento, arborização ou sustentabilidade
- [ ] Buscar "mobilidade urbana" retorna projetos de ciclovia, BRT, calçadas — mesmo sem essas palavras exatas no nome

## Riscos

- **Custo de embeddings:** Indexar todos os projetos do Oracle tem custo de API de embeddings. Estimar volume antes de iniciar.
- **Qualidade dos embeddings:** Descrições de projetos podem ser muito técnicas/abreviadas, gerando embeddings de baixa qualidade semântica
- **Manutenção do índice:** Projetos atualizados no Oracle não atualizam automaticamente o índice — risco de dessincronia
- **Esforço elevado:** Esta story pode justificar um Epic separado (Epic 2 — IA Semântica) dado o escopo. **Recomendação Pax (@po):** mover para Epic 2 durante sprint planning se o Epic 1 estiver próximo de concluído.
