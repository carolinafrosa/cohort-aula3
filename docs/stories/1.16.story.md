# Story 1.16 — Quick Wins de Qualidade SQL

**Status:** Ready
**Epic:** 1 — Qualidade e UX do Chatbot
**Story ID:** 1.16
**Prioridade:** Média
**Estimativa:** S (2–3h de edição no n8n)

---

## Descrição

Três problemas de qualidade pequenos e independentes identificados nas queries Oracle do fluxo. Todos são correções de 1–3 linhas com impacto real em performance, corretude ou manutenibilidade. Agrupados numa única story para evitar fragmentação excessiva do backlog.

**Valor:** Redução de I/O desnecessário no banco (DISTINCT + leitura dupla da view), eliminação de coluna fantasma no payload, e maior robustez da query de entregas — sem alteração funcional para o cidadão.

| # | Problema | Nó afetado |
|---|----------|-----------|
| A | `SELECT DISTINCT` desnecessário | `ConsultaValores1` |
| B | Coluna `SITUACAO_PROJETO` selecionada mas nunca usada | `ConsultaValores1` |
| C | `ConsultaDistintos` lê `VW_IDENTIFICACAO_PROJETOS` 2× | `ConsultaDistintos` |
| D | Colunas quoted com acentos em `ConsultaEntregas1` | `ConsultaEntregas1` |

> **Nota:** Correção de `ORDER BY` + padronização de `ROWNUM` em contratos é escopo exclusivo da **Story 1.18**. Implementar 1.16 antes ou depois de 1.18 — nunca em paralelo sobre o mesmo JSON.

## Acceptance Criteria

### AC-A: ConsultaValores1 — remover SELECT DISTINCT
- [ ] `SELECT DISTINCT` substituído por `SELECT` simples
- [ ] Coluna `SITUACAO_PROJETO` removida do SELECT (nunca usada pelo `FormataValores`)

**Antes:**
```sql
SELECT DISTINCT VALOR_PLANEJADO, VALOR_CONTRATADO_2_3 AS VALOR_CONTRATADO,
    VALOR_EXECUTADO_4_5 AS VALOR_EXECUTADO, VALOR_PAGO,
    PERCENTUAL_EXECUCAO_CONTRATADO AS PERC_EXEC, SITUACAO_PROJETO
FROM VW_BI_VDBEXECUCAOPROJETO
WHERE CODIGO_PROJETO = ...
```

**Depois:**
```sql
SELECT VALOR_PLANEJADO,
    VALOR_CONTRATADO_2_3 AS VALOR_CONTRATADO,
    VALOR_EXECUTADO_4_5 AS VALOR_EXECUTADO,
    VALOR_PAGO,
    PERCENTUAL_EXECUCAO_CONTRATADO AS PERC_EXEC
FROM VW_BI_VDBEXECUCAOPROJETO
WHERE CODIGO_PROJETO = ...
```

### AC-B: ConsultaDistintos — consolidar leitura da view
- [ ] As duas subqueries que leem `VW_IDENTIFICACAO_PROJETOS` (ORGAO + TIPO) são consolidadas usando a técnica de subquery única com MAX(CASE WHEN):

> **Nota para @dev:** Verificar se a view Oracle suporta `SELECT DISTINCT ORGAO, TIPO FROM VW_IDENTIFICACAO_PROJETOS` — se sim, uma única leitura retorna ambos. Alternativamente manter UNION ALL mas remover subquery redundante se a view já retorna dados distintos por linha.

**Simplificação viável (mesma lógica, menos I/O):**
```sql
SELECT 'ORGAO' AS TIPO_CAMPO, ORGAO AS VALOR
FROM (SELECT DISTINCT ORGAO FROM VW_IDENTIFICACAO_PROJETOS
      WHERE ORGAO IS NOT NULL ORDER BY ORGAO)
WHERE ROWNUM <= 200
UNION ALL
SELECT 'TIPO', TIPO
FROM (SELECT DISTINCT TIPO FROM VW_IDENTIFICACAO_PROJETOS
      WHERE TIPO IS NOT NULL ORDER BY TIPO)
WHERE ROWNUM <= 100
UNION ALL
SELECT 'MUNICIPIO', MUNICIPIO
FROM (SELECT MUNICIPIO FROM MUNICIPIO ORDER BY MUNICIPIO)
WHERE ROWNUM <= 300
```
*(sem alteração funcional — apenas confirmar que o resultado é idêntico ao atual)*

### AC-C: ConsultaEntregas1 — verificar colunas com acentos
- [ ] Confirmar que as colunas `"Cód. projeto"`, `"Tipo de informação"`, `"% Executada"` existem na view com exatamente esses nomes (case-sensitive, com acentos)
- [ ] Se a view tiver aliases sem acentos, usar os aliases na query para maior robustez
- [ ] Documentar no Change Log qual é o nome exato verificado no banco

## Riscos

- **AC-A:** Se `VW_BI_VDBEXECUCAOPROJETO` puder retornar mais de uma linha por `CODIGO_PROJETO`, remover `DISTINCT` pode quebrar `FormataValores` (que usa `todos[0]`). Verificar com `SELECT COUNT(*) FROM VW_BI_VDBEXECUCAOPROJETO WHERE CODIGO_PROJETO = {algum_id_real}` antes de aplicar.
- **AC-C:** Se as colunas de `VW_BI_VDBCRONOGRAMA` tiverem nomes diferentes dos esperados, a query falhará em runtime. Verificar `DESC VW_BI_VDBCRONOGRAMA` antes de fazer qualquer alteração.
