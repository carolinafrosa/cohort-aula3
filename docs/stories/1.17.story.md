# Story 1.17 — Refatorar MontaBusca: CTE BASE Único e Remover Limite de 200 Projetos

**Status:** Ready
**Epic:** 1 — Qualidade e UX do Chatbot
**Story ID:** 1.17
**Prioridade:** Alta
**Estimativa:** M (3–5h de edição no n8n)

---

## Descrição

O nó `MontaBusca` tem dois problemas estruturais na query principal:

**Problema 1 — WHERE avaliado 3 vezes:**
A mesma cláusula WHERE complexa (com `TRANSLATE`, múltiplos `LIKE`, `AND`) é copiada literalmente em três lugares: `MUNI_COUNTS`, `TOTAL_COUNT` e o SELECT principal. No Oracle 11g, CTEs podem ser inlined pelo otimizador, causando execução tripla da condição mais cara da query.

**Problema 2 — Limite de 200 projetos:**
`FETCH FIRST 200 ROWS ONLY` limita os projetos retornados ao n8n. Se uma busca retorna 500 projetos, `TOTAL_GERAL` mostra 500 (correto, via CTE), mas as estatísticas de refinamento (`topMunicipios`, `topOrgaos`, `topTipos`) são calculadas apenas sobre os 200 primeiros — enviesadas e incompletas.

A solução para ambos é um CTE `BASE` que materializa os IDs dos projetos que atendem à condição UMA VEZ, e todos os demais CTEs e o SELECT principal derivam dele — sem limite de linhas no BASE.

**Valor:** Query mais eficiente + estatísticas de refinamento precisas sobre o universo completo de resultados.

## Acceptance Criteria

### AC-1: CTE BASE adicionado — WHERE avaliado uma única vez

A query gerada por `MontaBusca` deve seguir a estrutura:

```sql
WITH BASE AS (
    -- WHERE avaliado UMA VEZ aqui
    SELECT DISTINCT VIP.PROJETO_ID
    FROM VW_IDENTIFICACAO_PROJETOS VIP
    LEFT JOIN LOCALIZACAO L      ON L.PROJETO_ID = VIP.PROJETO_ID
    LEFT JOIN MUNICIPIO M        ON M.ID = L.MUNICIPIO_ID
    WHERE {whereCompleto}
    -- SEM FETCH FIRST aqui — BASE contém todos os projetos que atendem à busca
),
MUNI_COUNTS AS (
    SELECT M.MUNICIPIO AS MC_MUN, COUNT(*) AS MC_CNT
    FROM BASE B
    JOIN VW_IDENTIFICACAO_PROJETOS VIP ON VIP.PROJETO_ID = B.PROJETO_ID
    LEFT JOIN LOCALIZACAO L ON L.PROJETO_ID = VIP.PROJETO_ID
    LEFT JOIN MUNICIPIO M   ON M.ID = L.MUNICIPIO_ID
    GROUP BY M.MUNICIPIO
),
TOTAL_COUNT AS (
    SELECT COUNT(*) AS TOTAL_GERAL FROM BASE
)
SELECT VIP.PROJETO_ID, VIP.NUMERO, VIP.ANO, ...
FROM BASE B
JOIN VW_IDENTIFICACAO_PROJETOS VIP ON VIP.PROJETO_ID = B.PROJETO_ID
LEFT JOIN MUNICIPIO M    ON M.ID = L.MUNICIPIO_ID
LEFT JOIN MUNICIPIO_REGIAO MR ON MR.MUNICIPIO_ID = M.ID
LEFT JOIN MUNI_COUNTS MC ON MC.MC_MUN = M.MUNICIPIO
CROSS JOIN TOTAL_COUNT TC
ORDER BY VIP.ANO DESC, VIP.NUMERO DESC
-- FETCH FIRST apenas no SELECT final, se necessário para proteção
```

- [ ] A string `whereCompleto` aparece apenas UMA vez na query (no CTE BASE)
- [ ] `MUNI_COUNTS` e `TOTAL_COUNT` derivam de `BASE`, não repetem o WHERE
- [ ] `TOTAL_GERAL` conta TODOS os projetos da busca (sem ser afetado por FETCH)

### AC-2: Limite de 200 projetos removido do CTE BASE

- [ ] O CTE `BASE` não tem `FETCH FIRST` nem `ROWNUM` — contém todos os projetos que atendem à condição
- [ ] `TOTAL_GERAL` reflete o número real de projetos, não limitado por FETCH
- [ ] As estatísticas de refinamento (`topMunicipios`, `topOrgaos`, `topTipos` calculadas em `ProcessaResultados`) são baseadas no conjunto completo

### AC-3: Proteção de memória no SELECT final

- [ ] O SELECT final (que retorna linhas ao n8n) mantém `FETCH FIRST 500 ROWS ONLY` para evitar retornar dezenas de milhares de projetos em buscas muito abertas
- [ ] O valor 500 é suficiente para paginação e refinamento sem risco de estouro de memória no processo n8n

> **Nota:** O `FETCH FIRST` no SELECT final NÃO afeta `TOTAL_GERAL` (que vem do CTE BASE) — afeta apenas quantas linhas de dados trafegam do Oracle para o n8n.

### AC-4: JOINs mortos removidos

- [ ] As 3 tabelas que estavam no SELECT principal mas nunca retornavam colunas são removidas:
  ```sql
  -- REMOVER estas linhas do SELECT principal:
  LEFT JOIN PORTFOLIO_PROJETO PP ON VIP.PROJETO_ID = PP.PROJETO_ID
  LEFT JOIN PORTFOLIO PORT        ON PP.PORTFOLIO_ID = PORT.ID
  LEFT JOIN PROGRAMA_INVESTIMENTO PI ON PI.ID = PP.PROGRAMA_INVESTIMENTO_ID
  ```
- [ ] As colunas `PORT.*`, `PP.*`, `PI.*` não são referenciadas em nenhum lugar (confirmado)

### AC-5: Sem regressão funcional

- [ ] Busca por código de processo retorna o projeto correto
- [ ] Busca por município retorna projetos do município
- [ ] `TOTAL_GERAL` exibido na mensagem de refinamento é correto
- [ ] Listas de municípios no refinamento refletem o universo completo (não apenas 200)

## Riscos

- **Memória do n8n:** Sem o limite de 200, uma busca muito genérica (ex: digitar apenas "a") pode retornar milhares de projetos. O `FETCH FIRST 500 ROWS ONLY` no SELECT final é a proteção. Monitorar após deploy.
- **Performance do Oracle:** O CTE BASE com `SELECT DISTINCT VIP.PROJETO_ID` precisa de um índice em `PROJETO_ID` na view ou na tabela base. Se não existir índice, o ganho do CTE pode ser menor que o esperado. Verificar o plano de execução (`EXPLAIN PLAN`) se disponível.
- **Oracle 11g e materialização de CTEs:** Oracle 11g não garante materialização de CTEs por padrão. Para forçar, pode ser necessário usar o hint `/*+ MATERIALIZE */` no CTE BASE se o otimizador insistir em inline. Testar e verificar o comportamento.
